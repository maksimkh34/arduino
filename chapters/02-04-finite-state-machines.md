# Глава 2.4. Конечные автоматы (FSM): управление состояниями устройства

## Зачем нужна эта глава

До сих пор наши устройства были реактивными, но простыми: кнопка нажата — светодиод включился, кнопка отпущена — светодиод выключился; событие нажатия найдено — счётчик увеличился. Для первых экспериментов этого достаточно. Но любое устройство, которое хоть немного похоже на реальный продукт, быстро перестаёт помещаться в одну переменную `buttonPressed` и пару `if`.

Представь кодовый замок. Он не просто проверяет, нажата ли кнопка. Он должен помнить, на каком шаге ввода находится пользователь: ждёт первую кнопку, вторую, третью, уже открылся, ошибся, заблокирован или ждёт сброса. Светофор тоже не просто включает LED. Он находится в одном из режимов: красный, красный+жёлтый, зелёный, мигающий зелёный, жёлтый. Каждое состояние имеет своё поведение и свои правила перехода дальше.

Если такое поведение писать как набор разрозненных флагов, код быстро превращается в клубок:

```cpp
if (buttonPressed && !locked && step == 2 && !timeoutExpired && !errorMode) {
  // кажется, что-то должно произойти
}
```

Senior Developer сразу узнаёт запах проблемы: состояние системы размазано по нескольким переменным, инварианты неявны, переходы трудно проверить, новые требования ломают старую логику. В embedded это особенно неприятно: ошибка не просто падает exception'ом, а включает не тот вывод, не реагирует на кнопку или зависает в режиме, из которого пользователь не может выйти.

Конечный автомат — один из самых полезных способов вернуть поведение под контроль. Он заставляет задать три вопроса:

1. В каких состояниях может находиться устройство?
2. Какие события устройство умеет принимать?
3. Какие переходы между состояниями разрешены?

Эта глава переводит код Arduino от «набора условий» к архитектуре поведения.

> **Интуиция**
>
> Конечный автомат похож на карту метро. Станции — это состояния. Поезд не телепортируется куда угодно: он переходит только по разрешённым линиям. Событие — это причина поехать дальше: нажали кнопку, истёк таймер, пришёл символ, сработал датчик. Хорошая программа устройства знает, на какой станции она сейчас и какие следующие станции разрешены.

## Что мы соберем к концу главы

К концу главы мы соберём четыре связанных проекта:

1. **Светофор на конечном автомате** — три LED проходят последовательность состояний без хаотичных `if`.
2. **Переключатель режимов LED по кнопке** — одно нажатие переводит устройство между режимами `OFF`, `ON`, `BLINK` и `SOS`.
3. **Простой кодовый замок на последовательности кнопок** — устройство помнит прогресс ввода и показывает успех или ошибку.
4. **Визуализатор состояния FSM** — отдельные LED показывают текущее состояние устройства, чтобы автомат можно было отлаживать глазами.

Все проекты используют компоненты из уже доступного набора: Arduino Mega 2560 R3, breadboard, кнопки, светодиоды, резисторы и провода.

## Карта путешествия

Мы начнём с проблемы: почему обычные `if` перестают масштабироваться. Затем введём модель FSM: состояния, события, переходы, действия на входе в состояние и действия внутри состояния. После этого соберём первый автомат — светофор. Затем усложним задачу: добавим кнопку, режимы, debounce и события нажатия. Дальше построим маленький кодовый замок, где порядок событий имеет значение. В последнем проекте сделаем инженерный инструмент — визуализацию текущего состояния.

Логика главы такая:

1. **Поведение устройства как модель.** Не «что сейчас нажато», а «в каком режиме находится система».
2. **FSM как контракт.** Разрешённые состояния и переходы фиксируются явно.
3. **`enum` и `switch/case`.** C++ даёт удобный синтаксис для читаемой реализации автомата.
4. **События от железа.** Кнопка после debounce превращается в дискретное событие `BUTTON_PRESSED`.
5. **Отладка состояний.** Состояние должно быть наблюдаемым: через Serial Monitor или LED.

## Ключевые термины

- **Конечный автомат (Finite State Machine, FSM)** — модель поведения системы, где в каждый момент времени система находится ровно в одном состоянии из конечного набора и переходит в другое состояние по событиям.
- **Состояние (state)** — режим работы устройства, определяющий, как оно реагирует на события и какие выходы включает.
- **Событие (event)** — дискретный факт, который может вызвать переход: нажатие кнопки, истечение времени, приход команды.
- **Переход (transition)** — правило изменения состояния при событии.
- **Действие (action)** — код, выполняемый при входе в состояние, выходе из состояния или во время пребывания в состоянии.
- **`enum`** — перечисление C/C++, удобный способ задать именованный конечный набор значений.
- **`switch/case`** — оператор выбора ветки кода по значению переменной; хорошо подходит для обработки текущего состояния.
- **Таблица переходов** — табличная запись FSM: текущее состояние + событие → новое состояние + действие.

## Практическая задача главы

Наша главная задача — научиться проектировать устройство, поведение которого зависит от прошлого, а не только от текущего состояния входов.

Кнопка в проекте 2.1 давала прямую реакцию: нажата — LED горит. Но в реальных устройствах одно и то же нажатие может означать разное:

- в режиме `OFF` — включить устройство;
- в режиме `ON` — перейти к миганию;
- в режиме настройки — подтвердить пункт меню;
- в режиме ошибки — сбросить тревогу.

Физически событие одно: кнопка замкнула контакт. Смысл события зависит от состояния системы. Именно это и делает FSM основной архитектурной идеей главы.

## Теория, которая нужна для решения задачи

### Почему состояние нельзя размазывать по флагам

В маленьком скетче часто хочется завести несколько `bool`:

```cpp
bool isOn = false;
bool isBlinking = false;
bool isError = false;
bool isLocked = false;
```

Проблема не в самих флагах. Проблема в том, что некоторые комбинации флагов бессмысленны. Например, устройство одновременно `isOn == false` и `isBlinking == true`. Или замок одновременно `isLocked == true` и `isOpen == true`. Компилятор такие противоречия не видит. Для него это допустимые значения.

FSM предлагает другой подход: если устройство может быть только в одном режиме из набора, пусть это будет одна переменная:

```cpp
enum DeviceState {
  STATE_OFF,
  STATE_ON,
  STATE_BLINKING,
  STATE_ERROR
};

DeviceState state = STATE_OFF;
```

Теперь невозможна комбинация «выключен и мигает одновременно». Состояние одно. Переходы явные. Поведение проще проверить.

> **Инженерная заметка**
>
> FSM — не «паттерн ради паттерна». Это способ уменьшить пространство невозможных состояний. Чем меньше невозможных комбинаций может выразить программа, тем меньше багов придётся ловить на реальном железе.

### Состояние, событие, переход и действие

FSM состоит из четырёх главных элементов.

**Состояние** отвечает на вопрос: «Где сейчас система?»

Примеры:

- `RED` — светофор показывает красный;
- `WAIT_FIRST_DIGIT` — замок ждёт первую кнопку кода;
- `OPEN` — замок открыт;
- `ERROR` — пользователь ввёл неверную последовательность;
- `BLINK_FAST` — LED мигает быстро.

**Событие** отвечает на вопрос: «Что произошло?»

Примеры:

- `TIMER_EXPIRED` — истёк интервал;
- `BUTTON_1_PRESSED` — нажата первая кнопка;
- `BUTTON_2_PRESSED` — нажата вторая кнопка;
- `RESET_PRESSED` — пользователь запросил сброс.

**Переход** отвечает на вопрос: «Куда перейти из текущего состояния при таком событии?»

Пример:

```text
RED + TIMER_EXPIRED -> RED_YELLOW
RED_YELLOW + TIMER_EXPIRED -> GREEN
GREEN + TIMER_EXPIRED -> YELLOW
YELLOW + TIMER_EXPIRED -> RED
```

**Действие** отвечает на вопрос: «Что сделать при переходе или в состоянии?»

Например, при входе в `GREEN` включить зелёный LED и выключить остальные.

> **Глубже**
>
> В теории автоматов часто различают автоматы Мили и Мура. В автомате Мура выход зависит только от состояния. В автомате Мили выход зависит от состояния и входного события. В этой главе мы в основном используем стиль Мура: состояние `RED` само определяет, какие LED включены. Это проще для embedded-отладки: посмотрел на LED — понял состояние.

### `enum`: конечный набор значений в коде

`enum` хорошо совпадает с идеей конечного автомата. Если у нас конечное число состояний, мы можем явно перечислить их в коде.

```cpp
enum TrafficState {
  TRAFFIC_RED,
  TRAFFIC_RED_YELLOW,
  TRAFFIC_GREEN,
  TRAFFIC_YELLOW
};
```

Для компилятора это целочисленные значения. Для человека — читаемые имена. В Arduino C++ обычный `enum` проще для новичка, чем `enum class`, потому что не требует квалификации вида `TrafficState::Red`. В промышленном C++ часто предпочли бы `enum class`, но в учебнике Arduino мы пока выбираем ясность и совместимость.

> **Ошибка новичка**
>
> Не называй состояние просто `RED`, если в большом проекте есть риск конфликтов имён. Лучше использовать префикс: `TRAFFIC_RED`, `LOCK_ERROR`, `MODE_BLINK`. У Arduino-проектов много глобальных имён, библиотек и констант, поэтому короткие общие названия могут неожиданно пересечься.

### `switch/case`: диспетчер состояния

Типичный обработчик FSM выглядит так:

```cpp
switch (state) {
  case TRAFFIC_RED:
    // логика красного состояния
    break;

  case TRAFFIC_GREEN:
    // логика зелёного состояния
    break;
}
```

`switch` читает текущую переменную состояния и выбирает ветку. `break` завершает ветку. Без `break` выполнение провалится в следующий `case` — иногда это используют специально, но в учебном embedded-коде чаще это ошибка.

> **Ошибка новичка**
>
> Пропущенный `break` в `switch/case` может создать очень странное поведение автомата: состояние вроде бы обработалось, но код сразу выполнил следующую ветку. Если устройство «перескакивает» режимы, проверь `break` первым делом.

### Событие кнопки — это не уровень входа

После глав 2.1–2.3 важно зафиксировать различие:

- `digitalRead(buttonPin) == LOW` — физический уровень на входе сейчас;
- `buttonPressedEvent == true` — событие: кнопка была нажата один раз после debounce.

FSM обычно должен реагировать на события, а не на сырой уровень. Иначе удержание кнопки будет многократно переключать состояние на каждой итерации `loop()`.

В этой главе мы будем использовать небольшую функцию debounce, которая возвращает `true` один раз на подтверждённое нажатие.

```cpp
bool readButtonPressedEvent() {
  // true появляется один раз на стабильный фронт нажатия
}
```

Это продолжение главы 2.3: там мы научились фильтровать нестабильный физический сигнал, здесь превращаем его в чистое событие для архитектуры поведения.

### Таблица переходов как документация и тест

Перед кодом полезно записать таблицу:

| Текущее состояние | Событие | Следующее состояние | Действие |
|---|---|---|---|
| `MODE_OFF` | `BUTTON_PRESSED` | `MODE_ON` | включить LED |
| `MODE_ON` | `BUTTON_PRESSED` | `MODE_BLINK` | подготовить мигание |
| `MODE_BLINK` | `BUTTON_PRESSED` | `MODE_SOS` | начать SOS-паттерн |
| `MODE_SOS` | `BUTTON_PRESSED` | `MODE_OFF` | выключить LED |

Такая таблица делает две вещи:

1. Помогает написать код без гадания.
2. Служит чеклистом для ручного тестирования.

Если поведение сломалось, можно не рассуждать абстрактно, а проверить конкретную строку: «В состоянии `MODE_BLINK` при `BUTTON_PRESSED` должен быть переход в `MODE_SOS`».

> **Математика в действии**
>
> FSM — объект дискретной математики. Его можно представить как ориентированный граф: вершины — состояния, рёбра — переходы, метки рёбер — события. Для Senior Developer это мост между теорией графов и физическим устройством: граф перестаёт быть абстракцией, он начинает включать реальные светодиоды.

### Действия на входе и внутри состояния

Есть два типа действий в FSM:

**Действие на входе (entry action)** — выполняется один раз при переходе в состояние. Например, при входе в `STATE_GREEN` включить зелёный LED и выключить остальные.

**Действие внутри состояния (in-state action)** — выполняется на каждой итерации `loop()`, пока система остаётся в этом состоянии. Например, в состоянии `STATE_BLINK` проверить таймер и переключить LED.

В коде это может выглядеть так:

```cpp
void enterState(TrafficState newState) {
  state = newState;
  switch (state) {
    case TRAFFIC_RED:
      digitalWrite(redPin, HIGH);
      digitalWrite(yellowPin, LOW);
      digitalWrite(greenPin, LOW);
      stateTimer = millis();
      break;
    // ...
  }
}

void updateState() {
  switch (state) {
    case TRAFFIC_RED:
      if (millis() - stateTimer >= RED_DURATION) {
        enterState(TRAFFIC_RED_YELLOW);
      }
      break;
    // ...
  }
}
```

Такое разделение делает код явным: когда мы входим в состояние, LED настраиваются один раз. Потом каждая итерация `loop()` проверяет условия перехода.

> **Инженерная заметка**
>
> Разделение на `enterState()` и `updateState()` напоминает паттерн игрового движка: `onEnter()`, `update()`, `onExit()`. В embedded это не оверинжиниринг, а способ избежать случайного повторного включения LED на каждом проходе `loop()`.

### Отделение чтения входов от обработки событий

Хорошая структура Arduino FSM выглядит так:

```cpp
void loop() {
  // 1. Прочитать входы
  bool button1Event = readButton1Event();
  bool button2Event = readButton2Event();
  
  // 2. Обработать события в контексте состояния
  if (button1Event) {
    handleButton1();
  }
  
  // 3. Обновить состояние
  updateState();
  
  // 4. Применить выходы
  applyOutputs();
}
```

Зачем такая структура?

- **Читаемость:** видно, что сначала опросили железо, потом обработали логику, потом применили результат.
- **Тестируемость:** можно эмулировать `button1Event = true` и проверить автомат без физической кнопки.
- **Deterministic timing:** входы читаются один раз за цикл, а не в случайных местах кода.

Для Senior Developer это естественная идея: отделить I/O от logic. В embedded это иногда нарушается ради производительности, но на Arduino Mega с 16 МГц удобство важнее лишних 20 микросекунд.

### Диаграмма состояний в текстовом виде

Конечные автоматы часто рисуют визуально: кружочки-состояния, стрелки-переходы. Для учебника без иллюстраций достаточно текстовой нотации:

```text
[STATE_OFF]
  on BUTTON_PRESSED -> STATE_ON

[STATE_ON]
  on BUTTON_PRESSED -> STATE_BLINK

[STATE_BLINK]
  on BUTTON_PRESSED -> STATE_OFF
  every loop: toggle LED if interval passed

[STATE_SOS]
  on BUTTON_PRESSED -> STATE_OFF
  every loop: execute SOS pattern
```

Это не стандарт, но понятно без специального инструмента.

### FSM в реальных устройствах

FSM — не академическая игрушка. Они используются:

- в протоколах связи: состояния `IDLE`, `CONNECTING`, `CONNECTED`, `ERROR`;
- в UI: состояния меню `MAIN_MENU`, `SETTINGS`, `CALIBRATION`;
- в управлении двигателями: `STOPPED`, `ACCELERATING`, `RUNNING`, `BRAKING`;
- в безопасности: `ARMED`, `DISARMED`, `TRIGGERED`, `LOCKOUT`;
- в медицинских устройствах: чёткие FSM для сертификации.

В промышленных embedded-системах FSM часто генерируются из графической диаграммы специальным инструментом (Simulink, Yakindu, QP framework). На Arduino мы пишем вручную, но принципы те же.

> **В реальных устройствах**
>
> Термостат, микроволновка, стиральная машина, светофор, система тревоги, контроллер двигателя — всё это FSM. Хороший embedded-инженер видит состояния даже в простой кнопке: `RELEASED`, `PRESSED`, `HELD`, `RELEASED_AFTER_HOLD`.

## Проект 2.4.1. Светофор на конечном автомате

### Идея проекта

Собираем трёхцветный светофор: красный, жёлтый, зелёный LED. Светофор проходит последовательность состояний:

1. `RED` (красный) — 5 секунд
2. `RED_YELLOW` (красный + жёлтый) — 2 секунды
3. `GREEN` (зелёный) — 5 секунд
4. `YELLOW` (жёлтый) — 2 секунды
5. обратно в `RED`

Задача — реализовать эту последовательность через FSM без `delay()`.

### Чему учит этот проект

- Как описать поведение устройства состояниями и переходами.
- Как использовать `enum` для состояний светофора.
- Как писать `switch/case` для обработки текущего состояния.
- Как использовать `millis()` для автоматических переходов по таймеру.
- Как отделить вход в состояние от пребывания в состоянии.

### Что понадобится

| Компонент | Количество |

| Arduino Mega 2560 R3 | 1 |
| Breadboard | 1 |
| Светодиод красный | 1 |
| Светодиод жёлтый | 1 |
| Светодиод зелёный | 1 |
| Резистор 220 Ом | 3 |
| Провода папа-папа | 6 |

### Схема подключения

**Принцип:**

Три светодиода подключаются к трём разным цифровым пинам. Каждый светодиод через токоограничивающий резистор 220 Ом. Катоды к GND.

**Пошаговая сборка:**

1. Размести три светодиода на breadboard с небольшим расстоянием между ними.
2. Красный LED: анод в `e10`, катод в `e11`.
3. Жёлтый LED: анод в `e15`, катод в `e16`.
4. Зелёный LED: анод в `e20`, катод в `e21`.
5. Резистор 220 Ом для красного: первый вывод в `a10` (соединён с анодом), второй вывод в `a8`.
6. Резистор 220 Ом для жёлтого: первый вывод в `a15`, второй в `a13`.
7. Резистор 220 Ом для зелёного: первый вывод в `a20`, второй в `a18`.
8. Провода от Arduino:
   - D9 → `a8` (к резистору красного LED)
   - D10 → `a13` (к резистору жёлтого LED)
   - D11 → `a18` (к резистору зелёного LED)
9. Катоды всех LED соединить с GND:
   - провод от `f11` к шине GND
   - провод от `f16` к шине GND
   - провод от `f21` к шине GND
   - или объединить перемычками на breadboard и один провод к GND Arduino.

### Код проекта

```cpp
// Пины светодиодов
const int redPin = 9;
const int yellowPin = 10;
const int greenPin = 11;

// Состояния светофора
enum TrafficState {
  TRAFFIC_RED,
  TRAFFIC_RED_YELLOW,
  TRAFFIC_GREEN,
  TRAFFIC_YELLOW
};

// Длительности состояний (миллисекунды)
const unsigned long RED_DURATION = 5000;
const unsigned long RED_YELLOW_DURATION = 2000;
const unsigned long GREEN_DURATION = 5000;
const unsigned long YELLOW_DURATION = 2000;

// Текущее состояние
TrafficState state = TRAFFIC_RED;

// Таймер состояния
unsigned long stateStartTime = 0;

void setup() {
  pinMode(redPin, OUTPUT);
  pinMode(yellowPin, OUTPUT);
  pinMode(greenPin, OUTPUT);
  
  Serial.begin(9600);
  
  // Войти в начальное состояние
  enterState(TRAFFIC_RED);
}

void loop() {
  updateState();
}

// Функция входа в состояние
void enterState(TrafficState newState) {
  state = newState;
  stateStartTime = millis();
  
  // Действие на входе: настроить LED
  switch (state) {
    case TRAFFIC_RED:
      digitalWrite(redPin, HIGH);
      digitalWrite(yellowPin, LOW);
      digitalWrite(greenPin, LOW);
      Serial.println("State: RED");
      break;
      
    case TRAFFIC_RED_YELLOW:
      digitalWrite(redPin, HIGH);
      digitalWrite(yellowPin, HIGH);
      digitalWrite(greenPin, LOW);
      Serial.println("State: RED_YELLOW");
      break;
      
    case TRAFFIC_GREEN:
      digitalWrite(redPin, LOW);
      digitalWrite(yellowPin, LOW);
      digitalWrite(greenPin, HIGH);
      Serial.println("State: GREEN");
      break;
      
    case TRAFFIC_YELLOW:
      digitalWrite(redPin, LOW);
      digitalWrite(yellowPin, HIGH);
      digitalWrite(greenPin, LOW);
      Serial.println("State: YELLOW");
      break;
  }
}

// Функция обновления состояния
void updateState() {
  unsigned long elapsed = millis() - stateStartTime;
  
  switch (state) {
    case TRAFFIC_RED:
      if (elapsed >= RED_DURATION) {
        enterState(TRAFFIC_RED_YELLOW);
      }
      break;
      
    case TRAFFIC_RED_YELLOW:
      if (elapsed >= RED_YELLOW_DURATION) {
        enterState(TRAFFIC_GREEN);
      }
      break;
      
    case TRAFFIC_GREEN:
      if (elapsed >= GREEN_DURATION) {
        enterState(TRAFFIC_YELLOW);
      }
      break;
      
    case TRAFFIC_YELLOW:
      if (elapsed >= YELLOW_DURATION) {
        enterState(TRAFFIC_RED);
      }
      break;
  }
}
```

### Что происходит в коде

**Глобальные константы:**

- `redPin`, `yellowPin`, `greenPin` — пины, к которым подключены LED. Использование именованных констант вместо магических чисел `9`, `10`, `11` делает код читаемым.
- `enum TrafficState` — определяет четыре состояния светофора. Для компилятора это числа 0, 1, 2, 3, но для программиста — понятные имена.
- Длительности состояний заданы как `const unsigned long` — хорошая практика: легко изменить время для всех вхождений.

**Переменные состояния:**

- `state` — текущее состояние FSM. Всегда содержит одно из значений `enum TrafficState`.
- `stateStartTime` — момент входа в текущее состояние. Используется для вычисления `elapsed` на каждой итерации.

**`setup()`:**

- Настраиваем пины как выходы.
- Открываем Serial Monitor для отладки.
- Явно входим в начальное состояние через `enterState(TRAFFIC_RED)`. Это настраивает LED и запоминает время старта.

**`loop()`:**

- Вызываем `updateState()`. Никаких `delay()`. `loop()` крутится свободно, FSM сам проверяет время.

**`enterState()`:**

Функция входа в состояние. Она делает три вещи:

1. Обновляет глобальную переменную `state`.
2. Запоминает время входа в `stateStartTime`.
3. Настраивает выходы через `switch/case`: включает нужные LED, выключает остальные, выводит имя состояния в Serial.

Важно: действия на вход выполняются один раз. Если бы мы писали `digitalWrite(redPin, HIGH)` в `updateState()`, то на каждой итерации `loop()` (тысячи раз в секунду) отправлялась бы команда на пин. Это работает, но неэффективно и концептуально неправильно.

**`updateState()`:**

Функция обновления состояния. Она вызывается на каждой итерации `loop()` и проверяет условия перехода.

- Вычисляем `elapsed = millis() - stateStartTime` — сколько времени мы в текущем состоянии.
- `switch (state)` выбирает ветку для текущего состояния.
- Внутри каждого `case` проверяем условие: `if (elapsed >= DURATION)`.
- Если условие истинно, вызываем `enterState(новое_состояние)`.

Обратите внимание: переходы линейные, но это не означает, что FSM не может иметь сложные ветвления. Здесь последовательность фиксирована: RED → RED_YELLOW → GREEN → YELLOW → RED. Но в следующих проектах мы добавим кнопки и переходы станут зависеть от событий.

**Отсутствие `default` в `switch`:**

В этом коде `default` не нужен: мы знаем, что `state` всегда содержит одно из четырёх значений `enum`. Однако в производственном коде иногда добавляют `default` для обработки «невозможной» ошибки. Для учебника мы оставляем код минималистичным.

### Что происходит в схеме

Каждый LED включён последовательно с резистором 220 Ом между пином Arduino и GND.

**Когда пин D9 установлен в HIGH:**

- Напряжение на пине ~5 В.
- Ток течёт через резистор 220 Ом → через красный LED → к GND.
- Красный LED имеет прямое падение напряжения ~1.8–2.0 В.
- Остальное падает на резисторе: примерно 3 В.
- Ток: `I ≈ 3 В / 220 Ом ≈ 14 мА` — безопасно и для пина (максимум 40 мА), и для типичного LED (номинальный ток 10–20 мА).

**Когда пин D9 установлен в LOW:**

- Напряжение на пине ~0 В.
- Разность потенциалов между пином и GND отсутствует → ток не течёт → LED выключен.

Три LED работают независимо. Одновременно может гореть один, два или все три — это зависит от комбинации HIGH/LOW на пинах. Светофор настраивает комбинацию так, чтобы соответствовать реальным правилам дорожного движения.

> **Физика**
>
> LED — нелинейный элемент. У него нет простого сопротивления в омическом смысле. Зависимость тока от напряжения экспоненциальная. Резистор нужен, чтобы ограничить ток: без него при прямом включении LED потянет столько тока, сколько может дать пин, и либо погаснет от перегрева, либо сгорит. Резистор работает как балласт.

### Как проверить работу

1. Загрузи скетч на Arduino Mega 2560 R3.
2. Открой Serial Monitor (9600 baud).
3. Наблюдай светофор:
   - Сначала горит только красный LED — 5 секунд.
   - Затем красный + жёлтый — 2 секунды.
   - Затем только зелёный — 5 секунд.
   - Затем только жёлтый — 2 секунды.
   - Цикл повторяется.
4. В Serial Monitor видна последовательность: `State: RED`, `State: RED_YELLOW`, `State: GREEN`, `State: YELLOW`.

Если всё работает правильно, ты видишь реальное воплощение FSM: состояние меняется автоматически, каждое состояние включает свою комбинацию выходов, переходы точны.

### Если не работает

**LED не горят вообще:**

- Проверь питание Arduino.
- Проверь, что скетч загружен (встроенный LED на пине 13 мигает при загрузке).
- Проверь полярность LED: анод (длинная ножка) должен идти к резистору и пину Arduino, катод к GND.
- Измерь напряжение на пинах D9, D10, D11 мультиметром или подключи заведомо исправный LED для проверки.

**LED горят, но не переключаются:**

- Открой Serial Monitor. Если там нет сообщений — возможно, неправильная скорость baud (должна быть 9600).
- Если сообщения есть, но LED не меняются, проверь соединения: возможно, провода от пинов D9/D10/D11 подключены к неправильным резисторам.
- Проверь, что `pinMode()` вызван для всех пинов.

**LED переключаются, но не в том порядке:**

- Возможно, перепутаны цвета LED или пины. Проверь, какой пин соответствует какому LED. Можно временно оставить только один `digitalWrite()` в каждом `case`, чтобы понять, какой LED за что отвечает.

**Serial Monitor показывает состояния, но слишком быстро или медленно:**

- Проверь константы длительности. Если время кажется неправильным, возможно, ошибка в значении (например, `2000` вместо `20000` для 20 секунд).

**LED мерцает или ведёт себя странно:**

- Проверь, что нет конфликта на breadboard: соседние ряды не должны случайно соединяться.
- Проверь, что все GND соединены правильно. Если у LED нет общего GND с Arduino, ток не потечёт.

### Идеи для развития

1. **Изменить длительности.** Сделай зелёный сигнал длиннее (10 секунд) и посмотри, как меняется ритм.
2. **Добавить мигание жёлтого.** В состоянии `TRAFFIC_YELLOW` перед переходом в `RED` заставь жёлтый LED мигать 3 раза. Для этого можно ввести подсостояния или счётчик миганий.
3. **Ночной режим.** Добавь пятое состояние `TRAFFIC_NIGHT_BLINK`, где мигает только жёлтый. Переход в этот режим можно сделать по кнопке (следующий проект покажет, как).
4. **Подсчёт циклов.** Добавь переменную `cycleCount`, которая увеличивается при каждом возвращении в `TRAFFIC_RED`. Выводи её в Serial.
5. **Таймер до следующего состояния.** В Serial Monitor показывай не только текущее состояние, но и оставшееся время до перехода.

## Проект 2.4.2. Переключатель режимов LED по кнопке

### Идея проекта

Один светодиод, одна кнопка, четыре режима:

1. `MODE_OFF` — LED выключен.
2. `MODE_ON` — LED постоянно включён.
3. `MODE_BLINK` — LED мигает с интервалом 500 мс.
4. `MODE_SOS` — LED мигает паттерном SOS (· · · — — — · · ·).

Каждое нажатие кнопки переводит устройство в следующий режим по циклу.

### Чему учит этот проект

- Как события от кнопки управляют переходами FSM.
- Как использовать debounce из главы 2.3 для генерации чистых событий.
- Как в одном состоянии (`MODE_BLINK`, `MODE_SOS`) выполнять циклические действия с разной логикой.
- Как FSM с кнопкой масштабируется: добавление нового режима не ломает старые.

### Что понадобится

| Компонент | Количество |
|---|---|
| Arduino Mega 2560 R3 | 1 |
| Breadboard | 1 |
| Светодиод | 1 |
| Резистор 220 Ом | 1 |
| Кнопка (tactile switch) | 1 |
| Провода папа-папа | 5 |

### Схема подключения

**Принцип:**

Светодиод подключается через резистор к пину D9. Кнопка подключается к пину D2 с использованием `INPUT_PULLUP` (без внешнего резистора).

**Пошаговая сборка:**

1. Размести LED на breadboard: анод в `e10`, катод в `e11`.
2. Резистор 220 Ом: первый вывод в `a10` (соединён с анодом LED), второй вывод в `a8`.
3. Провод от пина D9 Arduino к `a8`.
4. Провод от катода LED (`f11`) к шине GND.
5. Размести кнопку на breadboard так, чтобы её выводы были в рядах `e15` и `e17` (кнопка перекрывает центральный разрыв).
6. Провод от пина D2 Arduino к `a15` (один вывод кнопки).
7. Провод от `f17` (другой вывод кнопки) к шине GND.
8. Провод от шины GND breadboard к GND Arduino.

### Код проекта

```cpp
// Пины
const int ledPin = 9;
const int buttonPin = 2;

// Состояния устройства
enum DeviceMode {
  MODE_OFF,
  MODE_ON,
  MODE_BLINK,
  MODE_SOS
};

// Текущий режим
DeviceMode mode = MODE_OFF;

// Переменные debounce
unsigned long lastDebounceTime = 0;
const unsigned long debounceDelay = 50;
int lastButtonState = HIGH;
int buttonState = HIGH;

// Переменные для мигания
unsigned long lastBlinkTime = 0;
const unsigned long blinkInterval = 500;
bool ledBlinkState = false;

// Переменные для SOS
unsigned long sosStartTime = 0;
int sosStep = 0;

// Паттерн SOS: короткий сигнал (dit) 200ms, длинный (dah) 600ms, пауза между символами 200ms, между буквами 600ms
// S: · · · (3 dit)
// O: — — — (3 dah)
// S: · · · (3 dit)
const int sosPattern[] = {200, 200, 200, 200, 200, 200, 600, 600, 600, 600, 600, 600, 200, 200, 200, 200, 200, 200, 1000}; // последний элемент — длинная пауза перед повтором
const int sosPatternLength = 19;

void setup() {
  pinMode(ledPin, OUTPUT);
  pinMode(buttonPin, INPUT_PULLUP);
  
  Serial.begin(9600);
  
  enterMode(MODE_OFF);
}

void loop() {
  // Чтение события кнопки
  bool buttonPressedEvent = readButtonPressedEvent();
  
  if (buttonPressedEvent) {
    handleButtonPress();
  }
  
  // Обновление состояния режима
  updateMode();
}

// Функция входа в режим
void enterMode(DeviceMode newMode) {
  mode = newMode;
  
  switch (mode) {
    case MODE_OFF:
      digitalWrite(ledPin, LOW);
      Serial.println("Mode: OFF");
      break;
      
    case MODE_ON:
      digitalWrite(ledPin, HIGH);
      Serial.println("Mode: ON");
      break;
      
    case MODE_BLINK:
      digitalWrite(ledPin, LOW);
      lastBlinkTime = millis();
      ledBlinkState = false;
      Serial.println("Mode: BLINK");
      break;
      
    case MODE_SOS:
      digitalWrite(ledPin, LOW);
      sosStartTime = millis();
      sosStep = 0;
      Serial.println("Mode: SOS");
      break;
  }
}

// Функция обновления режима (in-state actions)
void updateMode() {
  switch (mode) {
    case MODE_OFF:
    case MODE_ON:
      // Ничего не делать — статические состояния
      break;
      
    case MODE_BLINK:
      if (millis() - lastBlinkTime >= blinkInterval) {
        lastBlinkTime = millis();
        ledBlinkState = !ledBlinkState;
        digitalWrite(ledPin, ledBlinkState ? HIGH : LOW);
      }
      break;
      
    case MODE_SOS:
      updateSOS();
      break;
  }
}

// Обработка нажатия кнопки
void handleButtonPress() {
  switch (mode) {
    case MODE_OFF:
      enterMode(MODE_ON);
      break;
      
    case MODE_ON:
      enterMode(MODE_BLINK);
      break;
      
    case MODE_BLINK:
      enterMode(MODE_SOS);
      break;
      
    case MODE_SOS:
      enterMode(MODE_OFF);
      break;
  }
}

// Чтение события нажатия кнопки с debounce
bool readButtonPressedEvent() {
  int reading = digitalRead(buttonPin);
  
  if (reading != lastButtonState) {
    lastDebounceTime = millis();
  }
  
  bool event = false;
  
  if ((millis() - lastDebounceTime) > debounceDelay) {
    if (reading != buttonState) {
      buttonState = reading;
      
      // Событие: falling edge (HIGH -> LOW, так как INPUT_PULLUP)
      if (buttonState == LOW) {
        event = true;
      }
    }
  }
  
  lastButtonState = reading;
  return event;
}

// Обновление SOS паттерна
void updateSOS() {
  unsigned long elapsed = millis() - sosStartTime;
  
  // Вычисляем суммарное время до текущего шага
  unsigned long cumulativeTime = 0;
  for (int i = 0; i < sosStep; i++) {
    cumulativeTime += sosPattern[i];
  }
  
  // Проверяем, не пора ли перейти к следующему шагу
  if (elapsed >= cumulativeTime + sosPattern[sosStep]) {
    sosStep++;
    
    // Если достигли конца паттерна, начать сначала
    if (sosStep >= sosPatternLength) {
      sosStep = 0;
      sosStartTime = millis();
    }
  }
  
  // Определяем состояние LED для текущего шага
  // Чётные шаги (0, 2, 4, ...) — LED включён (сигнал)
  // Нечётные шаги (1, 3, 5, ...) — LED выключен (пауза)
  if (sosStep % 2 == 0) {
    digitalWrite(ledPin, HIGH);
  } else {
    digitalWrite(ledPin, LOW);
  }
}
```

### Что происходит в коде

Этот проект использует те же принципы FSM, что и светофор, но добавляет два важных элемента: событие от кнопки и динамические действия внутри состояния.

**Структура состояний:**

`enum DeviceMode` описывает четыре режима. Переменная `mode` хранит текущий режим.

**Debounce кнопки:**

Функция `readButtonPressedEvent()` — это улучшенная версия debounce из главы 2.3. Она возвращает `true` ровно один раз на стабильное нажатие кнопки (falling edge от HIGH к LOW, так как используется `INPUT_PULLUP`).

Ключевые моменты:

- `reading` — сырое значение с пина.
- `lastButtonState` — значение на предыдущей итерации.
- Если `reading` изменился, обновляем `lastDebounceTime`.
- Если с момента последнего изменения прошло больше `debounceDelay` (50 мс), считаем сигнал стабильным.
- Если стабильное значение отличается от `buttonState`, это реальное изменение состояния кнопки.
- Если новое состояние `LOW` (кнопка нажата), возвращаем `event = true`.

Важно: функция возвращает `true` только один раз. Удержание кнопки не создаёт повторных событий.

**`loop()`:**

1. Читаем событие кнопки.
2. Если событие произошло, вызываем `handleButtonPress()`.
3. Обновляем состояние через `updateMode()`.

Эта структура чёткая: события обрабатываются в одном месте, переходы в другом, действия внутри состояния в третьем.

**`enterMode()`:**

Функция входа в режим. Для каждого режима выполняет начальные действия:

- `MODE_OFF`: выключить LED.
- `MODE_ON`: включить LED.
- `MODE_BLINK`: выключить LED, запомнить время, сбросить `ledBlinkState`.
- `MODE_SOS`: выключить LED, запомнить время старта паттерна, сбросить счётчик шагов `sosStep`.

Обратите внимание: действия на вход выполняются один раз. Например, в `MODE_BLINK` мы сбрасываем таймер один раз, а не на каждой итерации `loop()`.

**`updateMode()`:**

Функция обновления режима. Вызывается на каждой итерации `loop()`. Для каждого режима проверяет, нужно ли что-то делать:

- `MODE_OFF`, `MODE_ON`: ничего не делать — это статические состояния. LED уже настроен в `enterMode()`.
- `MODE_BLINK`: проверяем, прошёл ли интервал 500 мс с последнего переключения. Если да, инвертируем `ledBlinkState` и применяем к LED.
- `MODE_SOS`: вызываем отдельную функцию `updateSOS()`, которая реализует сложный паттерн.

**`handleButtonPress()`:**

Функция обработки события нажатия кнопки. Она реализует таблицу переходов:

| Текущий режим | Событие | Новый режим |
|---|---|---|
| `MODE_OFF` | `BUTTON_PRESSED` | `MODE_ON` |
| `MODE_ON` | `BUTTON_PRESSED` | `MODE_BLINK` |
| `MODE_BLINK` | `BUTTON_PRESSED` | `MODE_SOS` |
| `MODE_SOS` | `BUTTON_PRESSED` | `MODE_OFF` |

Код читается как таблица: `switch (mode)` выбирает текущий режим, внутри каждого `case` вызывается `enterMode(новый_режим)`. Простая, явная, расширяемая архитектура.

**`updateSOS()`:**

Функция реализует паттерн SOS. SOS в азбуке Морзе:

- **S**: три коротких сигнала (· · ·)
- **O**: три длинных сигнала (— — —)
- **S**: три коротких сигнала (· · ·)

Мы кодируем паттерн как массив длительностей в миллисекундах:

```cpp
const int sosPattern[] = {200, 200, 200, 200, 200, 200, 600, 600, 600, 600, 600, 600, 200, 200, 200, 200, 200, 200, 1000};
```

- Первые 6 элементов: три коротких сигнала по 200 мс + три паузы по 200 мс = S.
- Следующие 6: три длинных сигнала по 600 мс + три паузы по 600 мс = O.
- Следующие 6: снова S.
- Последний элемент (1000 мс) — пауза перед повтором паттерна.

Переменная `sosStep` хранит текущий шаг в паттерне.

Функция работает так:

1. Вычисляем `elapsed` — время с начала паттерна.
2. Вычисляем `cumulativeTime` — суммарное время всех шагов до текущего.
3. Если `elapsed >= cumulativeTime + sosPattern[sosStep]`, значит текущий шаг завершён → переходим к следующему шагу.
4. Если достигли конца массива, сбрасываем `sosStep` в 0 и начинаем паттерн заново.
5. Определяем состояние LED: чётные шаги (0, 2, 4, ...) — LED включён (сигнал), нечётные (1, 3, 5, ...) — LED выключен (пауза).

Эта логика сложнее простого мигания, но она тоже неблокирующая и помещается в одной функции. Если бы мы писали это через `delay()`, код превратился бы в монстра из вложенных задержек.

> **Математика в действии**
>
> Паттерн SOS — это конечный автомат внутри состояния FSM. Можно смотреть на него как на вложенный автомат: каждый шаг `sosStep` — это подсостояние. Переходы линейны и детерминированы. Это пример композиции автоматов: устройство в целом — FSM с четырьмя режимами, режим `MODE_SOS` сам содержит автомат из 19 шагов.

### Что происходит в схеме

Схема проста: один LED, одна кнопка.

**LED:**

Подключён через резистор 220 Ом к пину D9. Когда D9 = HIGH, LED горит. Когда D9 = LOW, LED выключен.

**Кнопка:**

Подключена между пином D2 и GND. Пин D2 настроен как `INPUT_PULLUP`, поэтому внутренний резистор (~20–50 кОм) подтягивает пин к +5 В.

- Кнопка не нажата: контакт разомкнут, пин подтянут к +5 В → `digitalRead(buttonPin)` возвращает `HIGH`.
- Кнопка нажата: контакт замкнут, пин соединяется с GND → `digitalRead(buttonPin)` возвращает `LOW`.

Именно поэтому в коде событие — это `buttonState == LOW`. Это инверсная логика `INPUT_PULLUP`, уже знакомая из главы 2.2.

**Дребезг:**

Физический контакт кнопки нестабилен первые 10–50 мс после нажатия (см. главу 2.3). Функция `readButtonPressedEvent()` фильтрует это: она ждёт 50 мс стабильного сигнала перед тем, как признать событие настоящим.

### Как проверить работу

1. Загрузи скетч на Arduino.
2. Открой Serial Monitor (9600 baud).
3. Нажми кнопку:
   - Первое нажатие: LED включается, Serial показывает `Mode: ON`.
   - Второе нажатие: LED начинает мигать с интервалом 500 мс, Serial показывает `Mode: BLINK`.
   - Третье нажатие: LED выполняет паттерн SOS (три коротких, три длинных, три коротких), Serial показывает `Mode: SOS`.
   - Четвёртое нажатие: LED выключается, Serial показывает `Mode: OFF`.
   - Цикл повторяется.

Если всё работает правильно, ты видишь FSM в действии: одна кнопка управляет переходами, каждое состояние имеет своё поведение, код чист и понятен.

### Если не работает

**LED не реагирует на кнопку:**

- Открой Serial Monitor. Если при нажатии кнопки ничего не печатается, проблема в чтении кнопки.
- Проверь подключение кнопки: один вывод к D2, другой к GND.
- Проверь, что в коде `pinMode(buttonPin, INPUT_PULLUP)` выполнен.
- Временно добавь `Serial.println(digitalRead(buttonPin));` в начало `loop()` и посмотри, меняется ли значение при нажатии.

**LED реагирует, но переключается много раз на одно нажатие:**

- Debounce работает неправильно или отключён. Проверь, что `debounceDelay = 50` и алгоритм debounce используется.
- Возможно, контакт кнопки очень плохой и дребезг длится дольше 50 мс. Попробуй увеличить `debounceDelay` до 100 мс.

**LED мигает в `MODE_BLINK`, но слишком быстро или медленно:**

- Проверь значение `blinkInterval`. 500 мс должно давать мигание примерно 1 Гц (1 раз в секунду полный цикл вкл/выкл).
- Убедись, что `lastBlinkTime = millis();` выполняется и в `enterMode()`, и при каждом переключении LED.

**SOS выглядит неправильно:**

- Временно выведи в Serial значение `sosStep` на каждой итерации `updateSOS()`, чтобы видеть прогресс паттерна.
- Проверь, что массив `sosPattern` содержит правильные длительности.
- Проверь логику чёт/нечёт для включения/выключения LED.

**Кнопка реагирует через раз:**

- Возможно, кнопка некачественная или плохо вставлена в breadboard. Попробуй другую кнопку.
- Проверь, что GND breadboard соединён с GND Arduino — без общего GND кнопка не работает.

### Идеи для развития

1. **Добавить пятый режим.** Например, `MODE_PULSE` — плавное нарастание и угасание яркости через PWM (будет подробно в разделе 4).
2. **Сделать SOS быстрее или медленнее.** Измени длительности в массиве `sosPattern`.
3. **Добавить вторую кнопку.** Одна переключает режимы вперёд, другая назад.
4. **Сохранить последний режим в EEPROM.** После перезагрузки Arduino устройство возвращается к тому режиму, в котором было выключено (EEPROM будет в разделе 5).
5. **Подсчитать количество нажатий.** Добавь переменную `clickCount` и выводи её в Serial каждый раз, когда кнопка нажата.

## Проект 2.4.3. Простой кодовый замок на последовательности кнопок

### Идея проекта

Три кнопки, один LED, одна задача: ввести правильную последовательность.

Правильный код: кнопка 1 → кнопка 2 → кнопка 3.

Если последовательность верная, LED включается на 3 секунды (замок открыт), затем возвращается в режим ожидания. Если пользователь ошибся, LED мигает быстро 3 раза (ошибка) и возвращается к началу.

Это первый проект, где порядок событий критичен. FSM должен помнить прогресс ввода.

### Чему учит этот проект

- Как FSM управляет последовательностями событий.
- Как реализовать состояния для каждого шага ввода.
- Как обрабатывать правильное и неправильное событие в зависимости от состояния.
- Как добавить состояния успеха и ошибки с временными действиями.
- Как проектировать таблицу переходов для устройства с несколькими входами.

### Код проекта

```cpp
// Пины
const int ledPin = 9;
const int button1Pin = 2;
const int button2Pin = 3;
const int button3Pin = 4;

// Состояния замка
enum LockState {
  LOCK_IDLE,           // Ожидание первой кнопки
  LOCK_WAIT_SECOND,    // Ожидание второй кнопки
  LOCK_WAIT_THIRD,     // Ожидание третьей кнопки
  LOCK_OPEN,           // Замок открыт (успех)
  LOCK_ERROR           // Ошибка ввода
};

// Текущее состояние
LockState state = LOCK_IDLE;

// Таймер состояния (для LOCK_OPEN и LOCK_ERROR)
unsigned long stateStartTime = 0;

// Переменные debounce для трёх кнопок
struct ButtonDebounce {
  int pin;
  unsigned long lastDebounceTime;
  int lastButtonState;
  int buttonState;
};

ButtonDebounce button1 = {button1Pin, 0, HIGH, HIGH};
ButtonDebounce button2 = {button2Pin, 0, HIGH, HIGH};
ButtonDebounce button3 = {button3Pin, 0, HIGH, HIGH};

const unsigned long debounceDelay = 50;

// Переменные для мигания ошибки
unsigned long lastErrorBlinkTime = 0;
int errorBlinkCount = 0;
bool errorBlinkState = false;

void setup() {
  pinMode(ledPin, OUTPUT);
  pinMode(button1Pin, INPUT_PULLUP);
  pinMode(button2Pin, INPUT_PULLUP);
  pinMode(button3Pin, INPUT_PULLUP);
  
  Serial.begin(9600);
  
  enterState(LOCK_IDLE);
}

void loop() {
  // Чтение событий от трёх кнопок
  bool button1Event = readButtonEvent(button1);
  bool button2Event = readButtonEvent(button2);
  bool button3Event = readButtonEvent(button3);
  
  // Обработка событий в контексте текущего состояния
  handleButtonEvents(button1Event, button2Event, button3Event);
  
  // Обновление состояния
  updateState();
}

// Функция входа в состояние
void enterState(LockState newState) {
  state = newState;
  stateStartTime = millis();
  
  switch (state) {
    case LOCK_IDLE:
      digitalWrite(ledPin, LOW);
      Serial.println("State: IDLE - Waiting for button 1");
      break;
      
    case LOCK_WAIT_SECOND:
      Serial.println("State: WAIT_SECOND - Waiting for button 2");
      break;
      
    case LOCK_WAIT_THIRD:
      Serial.println("State: WAIT_THIRD - Waiting for button 3");
      break;
      
    case LOCK_OPEN:
      digitalWrite(ledPin, HIGH);
      Serial.println("State: OPEN - Correct sequence! Lock open.");
      break;
      
    case LOCK_ERROR:
      digitalWrite(ledPin, LOW);
      errorBlinkCount = 0;
      errorBlinkState = false;
      lastErrorBlinkTime = millis();
      Serial.println("State: ERROR - Wrong sequence!");
      break;
  }
}

// Функция обновления состояния
void updateState() {
  switch (state) {
    case LOCK_IDLE:
    case LOCK_WAIT_SECOND:
    case LOCK_WAIT_THIRD:
      // Ожидание событий, ничего не делать
      break;
      
    case LOCK_OPEN:
      // Открыт 3 секунды, затем вернуться к IDLE
      if (millis() - stateStartTime >= 3000) {
        enterState(LOCK_IDLE);
      }
      break;
      
    case LOCK_ERROR:
      // Мигнуть LED 3 раза быстро (интервал 200 мс), затем вернуться к IDLE
      if (errorBlinkCount < 6) { // 6 переключений = 3 цикла вкл/выкл
        if (millis() - lastErrorBlinkTime >= 200) {
          lastErrorBlinkTime = millis();
          errorBlinkState = !errorBlinkState;
          digitalWrite(ledPin, errorBlinkState ? HIGH : LOW);
          errorBlinkCount++;
        }
      } else {
        enterState(LOCK_IDLE);
      }
      break;
  }
}

// Обработка событий кнопок
void handleButtonEvents(bool btn1, bool btn2, bool btn3) {
  switch (state) {
    case LOCK_IDLE:
      if (btn1) {
        enterState(LOCK_WAIT_SECOND);
      } else if (btn2 || btn3) {
        enterState(LOCK_ERROR);
      }
      break;
      
    case LOCK_WAIT_SECOND:
      if (btn2) {
        enterState(LOCK_WAIT_THIRD);
      } else if (btn1 || btn3) {
        enterState(LOCK_ERROR);
      }
      break;
      
    case LOCK_WAIT_THIRD:
      if (btn3) {
        enterState(LOCK_OPEN);
      } else if (btn1 || btn2) {
        enterState(LOCK_ERROR);
      }
      break;
      
    case LOCK_OPEN:
    case LOCK_ERROR:
      // В этих состояниях кнопки игнорируются
      break;
  }
}

// Чтение события кнопки с debounce
bool readButtonEvent(ButtonDebounce &btn) {
  int reading = digitalRead(btn.pin);
  
  if (reading != btn.lastButtonState) {
    btn.lastDebounceTime = millis();
  }
  
  bool event = false;
  
  if ((millis() - btn.lastDebounceTime) > debounceDelay) {
    if (reading != btn.buttonState) {
      btn.buttonState = reading;
      
      if (btn.buttonState == LOW) {
        event = true;
      }
    }
  }
  
  btn.lastButtonState = reading;
  return event;
}
```

### Что происходит в коде

Этот проект — первый пример FSM, где одно и то же событие (например, нажатие кнопки 1) приводит к разным результатам в зависимости от состояния.

**Таблица переходов:**

| Состояние | Кнопка 1 | Кнопка 2 | Кнопка 3 |
|---|---|---|---|
| `LOCK_IDLE` | → `LOCK_WAIT_SECOND` | → `LOCK_ERROR` | → `LOCK_ERROR` |
| `LOCK_WAIT_SECOND` | → `LOCK_ERROR` | → `LOCK_WAIT_THIRD` | → `LOCK_ERROR` |
| `LOCK_WAIT_THIRD` | → `LOCK_ERROR` | → `LOCK_ERROR` | → `LOCK_OPEN` |
| `LOCK_OPEN` | игнорировать | игнорировать | игнорировать |
| `LOCK_ERROR` | игнорировать | игнорировать | игнорировать |

Эта таблица — сердце логики замка. Если пользователь в состоянии `LOCK_IDLE` нажимает кнопку 1 — это правильно, переходим дальше. Если нажимает кнопку 2 или 3 — это ошибка.

**Структура `ButtonDebounce`:**

Мы используем `struct` для хранения данных debounce каждой кнопки. Это избавляет от копипаста переменных вроде `button1LastState`, `button2LastState` и т.д.

```cpp
struct ButtonDebounce {
  int pin;
  unsigned long lastDebounceTime;
  int lastButtonState;
  int buttonState;
};
```

Создаём три экземпляра:

```cpp
ButtonDebounce button1 = {button1Pin, 0, HIGH, HIGH};
```

Функция `readButtonEvent()` принимает ссылку на `ButtonDebounce` и работает с его полями. Это хороший пример абстракции: один алгоритм для трёх кнопок.

> **Глубже**
>
> В C++ `struct` — это почти то же, что `class`, но с открытыми полями по умолчанию. Для Arduino это удобный способ группировать связанные данные без overhead классов. В промышленном C++ такой `struct` мог бы быть классом `Button` с методами `update()` и `isPressed()`, но для учебника мы делаем шаг за шагом.

**`loop()`:**

1. Читаем события от трёх кнопок.
2. Передаём события в `handleButtonEvents()`, которая реализует таблицу переходов.
3. Вызываем `updateState()` для обработки автоматических переходов (таймеры в `LOCK_OPEN` и `LOCK_ERROR`).

**`enterState()`:**

Для каждого состояния выполняет начальное действие:

- `LOCK_IDLE`: выключить LED, напечатать сообщение.
- `LOCK_WAIT_SECOND`, `LOCK_WAIT_THIRD`: только сообщение (LED остаётся в том же состоянии).
- `LOCK_OPEN`: включить LED.
- `LOCK_ERROR`: выключить LED, сбросить счётчик миганий.

**`updateState()`:**

Обрабатывает автоматические переходы:

- В `LOCK_OPEN` ждёт 3 секунды, затем переходит в `LOCK_IDLE`.
- В `LOCK_ERROR` мигает LED 3 раза (6 переключений), затем переходит в `LOCK_IDLE`.

Логика мигания: переменная `errorBlinkCount` считает переключения LED. Каждые 200 мс состояние LED инвертируется. После 6 переключений переход в `LOCK_IDLE`.

**`handleButtonEvents()`:**

Ключевая функция. Реализует логику обработки событий:

- В `LOCK_IDLE`: если нажата кнопка 1 — переход в `LOCK_WAIT_SECOND`. Если кнопка 2 или 3 — переход в `LOCK_ERROR`.
- В `LOCK_WAIT_SECOND`: если нажата кнопка 2 — переход в `LOCK_WAIT_THIRD`. Если кнопка 1 или 3 — ошибка.
- В `LOCK_WAIT_THIRD`: если нажата кнопка 3 — переход в `LOCK_OPEN` (успех). Если кнопка 1 или 2 — ошибка.
- В `LOCK_OPEN` и `LOCK_ERROR`: события игнорируются (можно добавить `// ignore` комментарий, но пустой `case` тоже ясен).

Обратите внимание: логика читается напрямую из таблицы переходов. Если потребуется изменить код замка на другую последовательность (например, 2 → 1 → 3), достаточно изменить условия внутри `handleButtonEvents()`.

> **Инженерная заметка**
>
> В реальном замке такая таблица переходов часто хранится не в коде, а в массиве или EEPROM. Это позволяет менять код замка без перепрошивки. Но для учебного проекта жёстко закодированная последовательность проще и нагляднее.

**`readButtonEvent()`:**

Та же функция debounce, что в проекте 2.4.2, но теперь она принимает ссылку на `ButtonDebounce &btn` и работает с её полями. Это пример универсальной функции: один код для трёх кнопок.

### Что происходит в схеме

Три кнопки подключены идентично: каждая между своим пином Arduino и GND. Пины настроены как `INPUT_PULLUP`, поэтому в покое подтянуты к +5 В.

**Нажатие любой кнопки:**

- Контакт замыкается → пин соединяется с GND → `digitalRead()` возвращает `LOW`.
- Debounce фильтрует дребезг.
- Функция `readButtonEvent()` возвращает `true` один раз.

**LED:**

Подключён через резистор 220 Ом к пину D9. Управляется в зависимости от состояния:

- `LOCK_IDLE`, `LOCK_WAIT_SECOND`, `LOCK_WAIT_THIRD`: LED выключен.
- `LOCK_OPEN`: LED включён.
- `LOCK_ERROR`: LED мигает.

### Как проверить работу

1. Загрузи скетч на Arduino.
2. Открой Serial Monitor (9600 baud).
3. Наблюдай сообщения: `State: IDLE - Waiting for button 1`.
4. Нажми кнопку 1 → Serial: `State: WAIT_SECOND - Waiting for button 2`.
5. Нажми кнопку 2 → Serial: `State: WAIT_THIRD - Waiting for button 3`.
6. Нажми кнопку 3 → Serial: `State: OPEN - Correct sequence! Lock open.`, LED включается на 3 секунды.
7. Через 3 секунды LED выключается, Serial: `State: IDLE`.
8. Попробуй неправильную последовательность: нажми кнопку 2 в состоянии `IDLE` → Serial: `State: ERROR - Wrong sequence!`, LED мигает 3 раза быстро, затем возвращается в `IDLE`.

Если всё работает, ты видишь FSM, который помнит прогресс и различает правильные и неправильные последовательности.

### Если не работает

**Кнопки не реагируют:**

- Проверь подключение: пины D2, D3, D4 к одним выводам кнопок, другие выводы к GND.
- Проверь, что `pinMode(button1Pin, INPUT_PULLUP)` и аналогично для остальных кнопок выполнены в `setup()`.
- Временно добавь `Serial.println()` в `readButtonEvent()`, чтобы видеть, регистрируются ли события.

**LED не включается при правильной последовательности:**

- Проверь подключение LED: анод через резистор к D9, катод к GND.
- Проверь полярность LED.
- Временно добавь `Serial.println("LED ON");` в `case LOCK_OPEN` функции `enterState()` и проверь, вызывается ли этот код.

**LED не мигает при ошибке:**

- Проверь логику в `updateState()` для `LOCK_ERROR`. Убедись, что `errorBlinkCount` сбрасывается в 0 при входе в состояние.
- Проверь интервал мигания: 200 мс должно быть заметно.

**Замок принимает неправильную последовательность как правильную:**

- Проверь условия в `handleButtonEvents()`. Возможно, перепутаны `btn1`, `btn2`, `btn3`.
- Убедись, что каждая кнопка подключена к правильному пину: кнопка 1 к D2, кнопка 2 к D3, кнопка 3 к D4.

**Serial Monitor показывает состояния, но они переключаются хаотично:**

- Возможно, одна из кнопок дребезжит сильнее обычного или плохо вставлена в breadboard. Попробуй другие кнопки.
- Проверь, что все кнопки имеют общий GND с Arduino.

### Идеи для развития

1. **Изменить код замка.** Вместо последовательности 1 → 2 → 3 сделай 3 → 1 → 2 или 2 → 2 → 1. Измени условия в `handleButtonEvents()`.
2. **Добавить таймаут.** Если пользователь не нажимает следующую кнопку в течение 5 секунд, вернуться в `LOCK_IDLE`.
3. **Увеличить длину кода.** Добавь состояния `LOCK_WAIT_FOURTH`, `LOCK_WAIT_FIFTH` для последовательности из 5 кнопок.
4. **Сделать код программируемым.** Добавь режим настройки, где пользователь сам задаёт последовательность кнопок, и она сохраняется в EEPROM.
5. **Добавить второй LED для индикации прогресса.** Например, жёлтый LED мигает при каждом правильном шаге, а зелёный включается при успехе.
6. **Подсчитать количество попыток.** Добавь переменную `attemptCount` и выведи её в Serial после каждой ошибки.

## Проект 2.4.4. Визуализатор состояния FSM через LED

### Идея проекта

Отладка FSM через Serial Monitor удобна, но не всегда под рукой. Инженерный способ — сделать состояния видимыми через LED: каждому состоянию соответствует свой LED. Когда FSM переходит в новое состояние, загорается соответствующий индикатор.

Мы возьмём автомат из проекта 2.4.2 (четыре режима LED: OFF, ON, BLINK, SOS) и добавим четыре отдельных LED-индикатора состояния.

### Чему учит этот проект

- Как сделать состояние FSM наблюдаемым без Serial Monitor.
- Как отделить индикацию состояния от функциональных выходов.
- Как использовать LED для инженерной диагностики устройства.
- Как масштабируется схема при добавлении большего количества выходов.

### Код проекта

```cpp
// Пины
const int ledPin = 9;          // Основной функциональный LED
const int buttonPin = 2;

// Пины индикаторов состояния
const int ledOffIndicator = 10;
const int ledOnIndicator = 11;
const int ledBlinkIndicator = 12;
const int ledSosIndicator = 13;

// Состояния устройства
enum DeviceMode {
  MODE_OFF,
  MODE_ON,
  MODE_BLINK,
  MODE_SOS
};

// Текущий режим
DeviceMode mode = MODE_OFF;

// Переменные debounce
unsigned long lastDebounceTime = 0;
const unsigned long debounceDelay = 50;
int lastButtonState = HIGH;
int buttonState = HIGH;

// Переменные для мигания
unsigned long lastBlinkTime = 0;
const unsigned long blinkInterval = 500;
bool ledBlinkState = false;

// Переменные для SOS
unsigned long sosStartTime = 0;
int sosStep = 0;

const int sosPattern[] = {200, 200, 200, 200, 200, 200, 600, 600, 600, 600, 600, 600, 200, 200, 200, 200, 200, 200, 1000};
const int sosPatternLength = 19;

void setup() {
  pinMode(ledPin, OUTPUT);
  pinMode(buttonPin, INPUT_PULLUP);
  
  pinMode(ledOffIndicator, OUTPUT);
  pinMode(ledOnIndicator, OUTPUT);
  pinMode(ledBlinkIndicator, OUTPUT);
  pinMode(ledSosIndicator, OUTPUT);
  
  Serial.begin(9600);
  
  enterMode(MODE_OFF);
}

void loop() {
  bool buttonPressedEvent = readButtonPressedEvent();
  
  if (buttonPressedEvent) {
    handleButtonPress();
  }
  
  updateMode();
}

void enterMode(DeviceMode newMode) {
  mode = newMode;
  
  // Выключить все индикаторы
  digitalWrite(ledOffIndicator, LOW);
  digitalWrite(ledOnIndicator, LOW);
  digitalWrite(ledBlinkIndicator, LOW);
  digitalWrite(ledSosIndicator, LOW);
  
  switch (mode) {
    case MODE_OFF:
      digitalWrite(ledPin, LOW);
      digitalWrite(ledOffIndicator, HIGH); // Включить индикатор OFF
      Serial.println("Mode: OFF");
      break;
      
    case MODE_ON:
      digitalWrite(ledPin, HIGH);
      digitalWrite(ledOnIndicator, HIGH); // Включить индикатор ON
      Serial.println("Mode: ON");
      break;
      
    case MODE_BLINK:
      digitalWrite(ledPin, LOW);
      lastBlinkTime = millis();
      ledBlinkState = false;
      digitalWrite(ledBlinkIndicator, HIGH); // Включить индикатор BLINK
      Serial.println("Mode: BLINK");
      break;
      
    case MODE_SOS:
      digitalWrite(ledPin, LOW);
      sosStartTime = millis();
      sosStep = 0;
      digitalWrite(ledSosIndicator, HIGH); // Включить индикатор SOS
      Serial.println("Mode: SOS");
      break;
  }
}

void updateMode() {
  switch (mode) {
    case MODE_OFF:
    case MODE_ON:
      break;
      
    case MODE_BLINK:
      if (millis() - lastBlinkTime >= blinkInterval) {
        lastBlinkTime = millis();
        ledBlinkState = !ledBlinkState;
        digitalWrite(ledPin, ledBlinkState ? HIGH : LOW);
      }
      break;
      
    case MODE_SOS:
      updateSOS();
      break;
  }
}

void handleButtonPress() {
  switch (mode) {
    case MODE_OFF:
      enterMode(MODE_ON);
      break;
      
    case MODE_ON:
      enterMode(MODE_BLINK);
      break;
      
    case MODE_BLINK:
      enterMode(MODE_SOS);
      break;
      
    case MODE_SOS:
      enterMode(MODE_OFF);
      break;
  }
}

bool readButtonPressedEvent() {
  int reading = digitalRead(buttonPin);
  
  if (reading != lastButtonState) {
    lastDebounceTime = millis();
  }
  
  bool event = false;
  
  if ((millis() - lastDebounceTime) > debounceDelay) {
    if (reading != buttonState) {
      buttonState = reading;
      
      if (buttonState == LOW) {
        event = true;
      }
    }
  }
  
  lastButtonState = reading;
  return event;
}

void updateSOS() {
  unsigned long elapsed = millis() - sosStartTime;
  
  unsigned long cumulativeTime = 0;
  for (int i = 0; i < sosStep; i++) {
    cumulativeTime += sosPattern[i];
  }
  
  if (elapsed >= cumulativeTime + sosPattern[sosStep]) {
    sosStep++;
    
    if (sosStep >= sosPatternLength) {
      sosStep = 0;
      sosStartTime = millis();
    }
  }
  
  if (sosStep % 2 == 0) {
    digitalWrite(ledPin, HIGH);
  } else {
    digitalWrite(ledPin, LOW);
  }
}
```

### Что происходит в коде

Код почти идентичен проекту 2.4.2, но с добавлением LED-индикаторов состояния.

**Новые пины:**

```cpp
const int ledOffIndicator = 10;
const int ledOnIndicator = 11;
const int ledBlinkIndicator = 12;
const int ledSosIndicator = 13;
```

Каждый пин управляет отдельным LED, который показывает активное состояние FSM.

**`setup()`:**

Добавлены вызовы `pinMode()` для четырёх индикаторных LED.

**`enterMode()`:**

При входе в новое состояние:

1. Выключаем все четыре индикатора.
2. Включаем LED, соответствующий новому состоянию.

Например, при входе в `MODE_BLINK`:

```cpp
digitalWrite(ledOffIndicator, LOW);
digitalWrite(ledOnIndicator, LOW);
digitalWrite(ledBlinkIndicator, LOW);
digitalWrite(ledSosIndicator, LOW);

// ...

digitalWrite(ledBlinkIndicator, HIGH);
```

Такая логика гарантирует, что всегда горит ровно один индикатор — тот, который соответствует текущему состоянию.

> **Инженерная заметка**
>
> В промышленных устройствах индикация состояния — стандартная практика. Контроллеры двигателей, промышленные ПЛК, медицинские приборы, автомобильные блоки управления — все используют LED или дисплеи для индикации режима. Это позволяет диагностировать проблему без подключения к компьютеру. Если устройство зависло в неправильном состоянии, техник видит это сразу.

**Остальная логика:**

Функции `updateMode()`, `handleButtonPress()`, `readButtonPressedEvent()`, `updateSOS()` без изменений.

### Что происходит в схеме

Основной LED работает функционально: он включается, мигает или выполняет SOS в зависимости от режима.

Четыре индикаторных LED работают как табло: каждый подключён к своему пину, каждый показывает одно из четырёх состояний. Когда FSM переходит в `MODE_BLINK`, синий индикатор включается, остальные выключаются. Это визуальная карта состояния автомата.

Все LED подключены через резисторы 220 Ом для ограничения тока. Все катоды соединены с общим GND. Это стандартная топология для множественных LED на одной breadboard.

### Как проверить работу

1. Загрузи скетч на Arduino.
2. Наблюдай LED-индикаторы:
   - Сразу после загрузки горит красный LED (индикатор `MODE_OFF`), основной LED выключен.
3. Нажми кнопку:
   - Красный индикатор гаснет, загорается жёлтый (индикатор `MODE_ON`), основной LED включается.
4. Нажми кнопку снова:
   - Жёлтый гаснет, загорается синий (индикатор `MODE_BLINK`), основной LED начинает мигать.
5. Нажми кнопку снова:
   - Синий гаснет, загорается белый (индикатор `MODE_SOS`), основной LED выполняет SOS-паттерн.
6. Нажми кнопку снова:
   - Белый гаснет, загорается красный, основной LED выключается.

Теперь состояние FSM видимо глазами. Не нужен Serial Monitor. Ты видишь, где находится автомат, без подключения к компьютеру.

### Если не работает

**Индикаторы не горят:**

- Проверь подключение каждого индикатора: пины D10, D11, D12, D13.
- Проверь полярность LED.
- Проверь резисторы: каждый индикатор должен иметь свой резистор 220 Ом.
- Временно замени `digitalWrite(ledOffIndicator, HIGH);` на `digitalWrite(ledOffIndicator, HIGH); delay(2000);` в `setup()`, чтобы проверить, что пин работает.

**Горят несколько индикаторов одновременно:**

- Проверь, что в начале `enterMode()` все индикаторы выключаются.
- Проверь, что нет случайных соединений на breadboard между пинами D10–D13.

**Индикаторы работают, но не соответствуют режиму:**

- Проверь, какой LED подключён к какому пину. Возможно, цвета перепутаны.
- Используй Serial Monitor для проверки: сообщение в Serial должно совпадать с горящим индикатором.

**Основной LED не работает, но индикаторы работают:**

- Проверь подключение основного LED к пину D9.
- Проверь, что логика управления основным LED не изменилась.

### Идеи для развития

1. **Добавить пятый режим и пятый индикатор.** Например, `MODE_PULSE` — плавное дыхание LED через PWM (будет в разделе 4).
2. **Использовать разные яркости индикаторов.** Через PWM можно сделать активный индикатор ярким, а остальные — тускло подсвеченными, чтобы видеть все состояния одновременно.
3. **Добавить семисегментный индикатор.** Вместо четырёх LED показать номер состояния на семисегментном дисплее (будет в разделе 6).
4. **Логировать переходы в EEPROM.** Сохранять историю переходов состояния для посмертной диагностики (будет в разделе 5).
5. **Сделать режим автоматической демонстрации.** Зажать кнопку на 3 секунды → устройство автоматически переключается между режимами раз в 5 секунд для демонстрации.

## Эксперименты

После четырёх проектов ты знаешь, как работают FSM. Теперь можно экспериментировать.

### Эксперимент 1: FSM с петлями

Измени таблицу переходов в проекте 2.4.2 так, чтобы из `MODE_BLINK` кнопка возвращала в `MODE_ON`, а не переходила в `MODE_SOS`. Получится петля: OFF → ON → BLINK → ON → BLINK → ... Попробуй реализовать и проверь, как меняется поведение.

### Эксперимент 2: FSM с таймаутами

Добавь в светофор (проект 2.4.1) состояние `TRAFFIC_ALL_RED`, где все три LED включены одновременно на 1 секунду перед переходом от `YELLOW` к `RED`. Это имитация аварийного режима перекрёстка.

### Эксперимент 3: FSM с счётчиком событий

В проекте 2.4.2 добавь переменную `modeChangeCount`, которая увеличивается при каждом переходе. Если счётчик достиг 20, устройство автоматически переходит в `MODE_OFF` и выводит сообщение: `Too many mode changes. Cooling down.` Через 10 секунд счётчик сбрасывается, и устройство снова принимает команды.

### Эксперимент 4: Вложенный FSM

В проекте 2.4.3 добавь режим `LOCK_PROGRAMMING`, в который можно войти, зажав все три кнопки одновременно. В этом режиме пользователь задаёт новую последовательность, которая сохраняется и используется при следующих проверках.

## Частые ошибки главы

### Ошибка 1: Забыть `break` в `switch/case`

**Симптом:** Устройство «проваливается» через несколько состояний сразу.

**Причина:** Отсутствие `break` в конце `case`. Компилятор не ругается, но выполнение продолжается в следующий `case`.

**Решение:** Всегда заканчивай каждый `case` оператором `break`, если не хочешь fall-through поведения.

### Ошибка 2: Обрабатывать уровень входа вместо события

**Симптом:** Удержание кнопки вызывает многократные переходы. Устройство «перескакивает» режимы.

**Причина:** Вместо события `buttonPressedEvent` используется `digitalRead(buttonPin) == LOW` напрямую в условии перехода. На каждой итерации `loop()` (тысячи раз в секунду) условие истинно, пока кнопка удерживается.

**Решение:** Использовать событие, которое возвращает `true` один раз на нажатие, а не текущий уровень входа.

### Ошибка 3: Не сбрасывать таймер при входе в состояние

**Симптом:** Переход по таймеру происходит немедленно или через непредсказуемое время.

**Причина:** Переменная `stateStartTime` не обновляется при входе в состояние. `elapsed` вычисляется от старого времени.

**Решение:** Всегда обновляй `stateStartTime = millis();` в функции `enterState()`.

### Ошибка 4: Размазать состояние по нескольким переменным

**Симптом:** Код становится запутанным, появляются невозможные комбинации флагов.

**Причина:** Вместо одной переменной `state` используется набор `bool isOn, bool isBlinking, bool isError`.

**Решение:** Если устройство может быть только в одном режиме из набора, используй `enum` и одну переменную состояния.

### Ошибка 5: Вызывать действия на вход в каждом `loop()`

**Симптом:** LED включается и выключается тысячи раз в секунду (хотя невидимо глазу). Serial Monitor заполняется одинаковыми сообщениями.

**Причина:** Действия на вход (например, `digitalWrite(ledPin, HIGH)`) вызываются в `updateState()` без проверки, вошли ли мы в состояние только что.

**Решение:** Отделить действия на вход (в функции `enterState()`, вызывается один раз) от действий внутри состояния (в `updateState()`, вызывается каждую итерацию `loop()`).

## Мини-проекты

Попробуй реализовать самостоятельно:

1. **Двухкнопочный светофор.** Одна кнопка переключает светофор вперёд, другая назад по последовательности состояний.
2. **Таймер с кнопкой старт/стоп.** Три состояния: `IDLE` (ждёт старта), `RUNNING` (считает секунды), `PAUSED` (пауза). Одна кнопка управляет переходами. LED показывает, идёт ли отсчёт (мигает в `RUNNING`, постоянно горит в `PAUSED`, выключен в `IDLE`).
3. **Замок с попытками.** Расширь проект 2.4.3: после трёх неправильных попыток устройство переходит в состояние `LOCK_BLOCKED` на 30 секунд, где не принимает кнопки вообще.
4. **FSM с голосовыми командами через Serial.** Вместо кнопок отправляй команды `ON`, `OFF`, `BLINK`, `SOS` через Serial Monitor, и устройство меняет режим.

## Что мы теперь умеем

После этой главы ты можешь:

- **Проектировать поведение устройства как FSM:** определить состояния, события, переходы и действия.
- **Реализовывать FSM в коде Arduino:** использовать `enum` для состояний, `switch/case` для обработки, отделять вход в состояние от обновления состояния.
- **Интегрировать события от кнопок:** превращать физические нажатия в чистые дискретные события через debounce.
- **Визуализировать состояние FSM:** делать состояние наблюдаемым через LED или Serial Monitor для диагностики.
- **Избегать «флагового ада»:** вместо хаоса `bool` использовать явную модель состояний.

Конечный автомат — один из самых полезных инструментов embedded-разработчика. Он превращает «какой-то код, который вроде работает» в структуру, которую можно понять, протестировать и развить.

## Как это пригодится дальше

FSM — фундамент для многих тем учебника:

- **Раздел 3 (Время и многозадачность):** FSM станет способом управлять несколькими задачами с разными интервалами без RTOS.
- **Раздел 7 (Клавиатуры и пульты):** Меню на LCD или матрице — это FSM, где каждый экран меню — состояние, каждая кнопка — событие.
- **Раздел 8 (UART и Serial):** Протоколы обмена данными — это FSM: `IDLE`, `RECEIVING_HEADER`, `RECEIVING_DATA`, `VALIDATING_CHECKSUM`.
- **Раздел 10 (I2C):** Мастер I2C — это FSM: `START`, `ADDRESS`, `DATA`, `STOP`.
- **Раздел 14 (Прерывания):** Прерывания могут генерировать события для FSM: кнопка, таймер, UART.
- **Раздел 15 (ШИМ и моторы):** Управление двигателем — FSM: `STOPPED`, `FORWARD`, `BACKWARD`, `BRAKING`.
- **Раздел 18 (Финальные проекты):** Любой комплексный проект (умный замок, погодная станция, игра) строится вокруг FSM.

FSM делает embedded-код не просто набором функций, а архитектурой поведения. Это мост между программированием и инженерией систем.
